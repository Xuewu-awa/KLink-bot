## ⭐ 事件契约：这才是最大的单点缺口

> 这一节是因为朋友发来一份 **KardsTranspiler**（另一个项目：把 Kismet 字节码直译成 C#）
> 的产物 `card_event_convoy_175.g.cs` 才发现的。那份文件里有这么一行：
>
> ```csharp
> public static Val OnPlayedFromHand(IHost H, Val self, Val[] args)
> {
>     L["targetCard"] = args.Length > 0 ? args[0] : Val.Nothing;
>     H.SetVar("K2Node_Event_targetCard", GetLocal(L, "targetCard"));   // ← 就是这个
>     _ = H.Call("ExecuteUbergraph_card_event_convoy_175", new Val[] { self, Val.Of(10) });
> }
> ```
>
> 顺着这条线回原始字节码，发现每个事件桩函数的形状是：
>
> ```
> LetValueOnPersistentFrame  K2Node_Event_attackerCard       = <局部 attackerCard>
> LetValueOnPersistentFrame  K2Node_Event_damageToDefender   = <局部 damageToDefender>
> LocalFinalFunction ExecuteUbergraph_<卡>  <入口下标>
> ```
>
> 也就是：**事件参数 → 持久帧槽位**的绑定在桩函数里；
> ubergraph 里再用 `槽位.成员`（IR 里就是 `ctx` 限定读取）去取值。

### 规模（`tools/extract-event-contracts.py` 抽出来的实测）

**172 个事件**，每个带 1–6 个**有类型**的参数。注册卡数最多的：

| 事件 | 卡数 | 参数 |
|---|---|---|
| `OnPlayedFromHand` | 992 | `targetCard` ✅ 已处理 |
| `OnEndOfTurn` | 188 | `turnnumber:Int` ⚠️ 引擎传 null |
| `OnStartOfTurn` | 155 | `turnnumber:Int` ⚠️ 引擎传 null |
| `OnOtherCardPlayedFromHand` | 131 | `cardPlayed` ❌ 没发 |
| `OnEnterPlay` | 91 | `method:EOnEnterPlayMethod` ❌ 没发 |
| `OnOtherCardEnterPlay` | 84 | `cardPlayed, method` ❌ 没发 |
| `OnDestroyed` | 79 | `killer, TriggerNotDestroyed:Bool` ⚠️ 载荷不符 |
| `OnOtherCardDestroyed` | 69 | `cardDestroyed, killer, destroyedInCombat, destroyedLocation, TriggerNotDestroyed, selfIsAlsoGettingDestroyed` ❌ |
| `OnLeaveBoardOrOwner` | 66 | `goingToLocation:ECardLocationEnum, leavePlayMethod` ❌ |
| `OnHandTargetSelected` | 49 | `handTargetCardID, instigatorID` ❌ |
| `OnOtherCardDrawnFromDeck` | 43 | `drawnCardID, drawnSide, StartOfTurnDraw` ❌ |
| `OnAfterAttack` | 40 | `defenderCard, wasShockAttack, attackCost` ⚠️ 载荷不符 |

### 引擎现状

引擎只发 **10 个**事件名，而且**连这 10 个的载荷都是错的**：

| 引擎发的 | 游戏声明的 | 问题 |
|---|---|---|
| `FireTrigger("OnStartOfTurn", null, side)` | `(Int turnnumber)` | 参数整个没绑 |
| `FireTrigger("OnAfterAttack", attacker, …)` | `(defenderCard, wasShockAttack, attackCost)` | 把「事件主体」当成了「参数」 |
| `FireTrigger("OnDestroyed", …)` | `(killer, TriggerNotDestroyed)` | 同上 |
| `FireTrigger("OnMoveToFrontline", …)` | `(ForceMove:Bool, moveCost:Int)` | 同上 |

**根因是一个，不是 172 个**：引擎的触发签名是「一个通用 subject」，
而游戏是「每个事件一张有类型的参数表」。
再加上 `ctx` 限定读取没实现 —— 这两件事是**同一个机制的两半，必须一起修**：

1. IR 生成器补出事件桩里的 `参数 → 持久帧槽位` 映射
   （现在被丢掉了：`gen-kismet-ir.py` 读 `Variable Name`，
   而 `LetValueOnPersistentFrame` 用的是 `Property Name`，所以 `dst` 是空串）
2. `FireTrigger` 改成按事件契约传载荷
3. `KismetVm.Eval` 实现 `ctx` 限定成员读取，`Frame` 绑定持久帧槽位

契约表已抽出：**`docs/event-contracts.json`**（172 个事件的名字、参数名、类型、槽位）。

## 关键判断

1. **工程侧已经到位**：950 局无异常、百万局只差约 2 小时（单线程）。
   训练吞吐**不是瓶颈**。
2. **瓶颈是规则保真度**，而且高度集中：
   - `ctx` 一个根因 → 142 张卡（53% 的元卡组卡）
   - 前 5 个原语 → 82% 的缺口触发
   - 9 张无蓝图卡 → 高频
3. **在保真度修好之前，自对弈的胜率数字没有意义**。
   现在跑出 175:25 这种极端比例，是 bug 的噪声，**不是卡组强度信号**。
   所以「写决策树 → 自对弈 → 采数据」这条链现在还不能信。
4. **验证手段本身有上限**：动作流只带 HQ 一个状态量。
   要逐帧对拍棋盘（前线槽位、单位数值、关键字），
   还需要客户端侧的状态导出 —— 这是目前唯一「拿不到就必须造」的东西。

### ⭐ 实验：把真实回放同时喂给两个引擎，逐条对拍

工具：`tools/SimCompare`（引用我的 `KLink.Bot` + 它的 `KardsSim.dll`）

```powershell
dotnet build ref\kards-sim\KardsSim\KardsSim.csproj -c Release   # 先单独编译它
dotnet run --project tools\SimCompare -c Release                 # 默认跑 310284 / 165924 / 955337
```

**为什么要逐条对拍**：单独看「各自的 HQ 一致率」会被「各自应用了多少条动作」污染 ——
应用得少的一方 HQ 不动，既容易“看起来一致”，也容易在别处对不上。
只有按 `actionId` 对齐、并只在**两边都成功应用**的动作上比较，数字才可比。

| 对局 | 可比动作 | 两边一致 | 只有我对 | 只有它对 |
|---|---|---|---|---|
| **310284** | 60 | **56** | 4 | **0** |
| 165924 | 8 | **8** | 0 | 0 |
| 955337 | 15 | **15** | 0 | 0 |

> ⚠️ 第一版跑出来是「只有我对 12、只有它对 0」，我差点得出「它比我差」的结论。
> 查下去发现是**我的驱动器 bug**：回放里 HQ 是一张卡（左 1 / 右 41），
> 而它的引擎用 `TargetId = 0` 表示敌方 HQ —— 我映射成了 `-1`，
> 于是「打 HQ」这个动作在它那边根本不成立。修掉后 12 处分歧变成 4 处。
> **这个教训值得记住：跨实现对拍时，先把驱动器本身的映射错误排除掉。**

### 两边**同时**对不上的地方：A36 那 3 点伤害

```
310284 A35  AC 7_schutzen 打 m16_halftrack
310284 A36  XActionEndOfTurn      对手HQ 期望 15
            我算出 18      它也算出 18      ← 完全一样
```

**两个互相独立的实现，在同一个动作上、以同一个数值对不上。**
这比单独一个实现对不上强得多 —— 说明问题很可能不在"某个引擎的规则写错了"，而在：

1. **动作流漏记了一条动作**（这局本来就有 A73..A76 四条完全相同的重复记录，
   证明录制的动作流与真实操作不是 1:1），或
2. 一个**两边都没实现**的效果（两边的效果逻辑同源，所以共享盲点很合理）

这是目前保真度上**唯一的、也是最有价值的**未决问题。

### ✅ 两边**同时**对不上的地方已经查明：A36 那 3 点伤害

```
310284 A35  AC 7_schutzen 打 m16_halftrack     （摧毁了它）
310284 A36  XActionEndOfTurn      对手HQ 期望 15
            我算出 18      它也算出 18      ← 两个独立实现同时错
```

**答案：`card_unit_7_schutzen` 在战斗中摧毁单位后会「变成老兵」，
而「变成老兵」这个动作本身会对敌方 HQ 造成 3 点伤害。**

它自己直译出来的代码（`Generated/Germany/BrothersInArms/units/card_unit_7_schutzen.g.cs`）：

```csharp
// 入口 10 = OnOtherCardDestroyed(cardDestroyed, killer, TriggerNotDestroyed,
//                                destroyedLocation, selfIsAlsoGettingDestroyed, destroyedInCombat)
if (selfIsAlsoGettingDestroyed) return;
if (!destroyedInCombat) return;                 // ← 关键守卫
if (!IsSideActive(self.side)) return;
if (!IsUnit(cardDestroyed)) return;
if (killer.cardID != self.cardID) return;       // 击杀者必须是我
if (IsVeteran(self)) return;
MakeVeteran(self);                              // → 触发 OnBecomingVeteran

// 入口 352 = OnBecomingVeteran
side = GetOppositeSide();
hq   = GetLocationCardBySide(side);             // 敌方 HQ
DamageCard(hq, 3, self.cardID, ...);            // ← 3 点 ✓
```

**卡面只写了「Becomes Veteran when it attacks and destroys a unit」——
变成老兵带来的「奖励」就是打敌方 HQ 3 点，文本里没写。**
所以 A35 摧毁半履带车 → 变老兵 → 左方 HQ 18→15 ✓ 完全闭合。

推论：**动作流没有漏记**，那个假设可以排除了。

### 两个实现为什么都漏掉它（同一种病，不同的表现）

| | 原因 |
|---|---|
| **kards-sim** | `Bridge/CardDispatch.cs` 的 `Fire` **最多只传 2 个实参**：<br>`var args = subject is null ? new[] { self } : new[] { self, Val.Ref(host.Obj(subject)) };`<br>直译产物用 `args.Length > n` 守卫，所以 `destroyedInCombat` 拿到 `Val.Nothing` → `if (!destroyedInCombat) return` **直接短路**。<br>它自己的注释就承认了这个限制：「多传的参数在直译产物里由 args.Length 守卫，不会越界」。 |
| **我这边** | `card_unit_7_schutzen` **根本不在我的 `card-ir.json` 里**（这局有 10 张卡缺失，包括在场上的 `stug_iii` 和 `ju_87_stuka`）。<br>另外我的触发派发同样只传一个通用 subject，没有 `killer` / `destroyedInCombat` 这些载荷。 |

### 修订后的判断

原先我说「我的内核只有 24% 的卡可信任，所以瓶颈是保真度」——
那是**静态**指标（ctx 未实现、66 个原语缺失）。**动态**对拍给出的图景要好得多：

- 两个独立实现都能把 310284 真实复现到**第 9~10 回合**（共 21 回合）
- 在两边都成功应用的动作上，**93% 完全一致**（56+8+15 = 79 / 83）
- 剩余偏差**收敛到单独一个事件**

也就是说：**模拟器这一层比我上次估的近得多**，
主要遗留问题不是"几百张卡要修"，而是**一个待解释的事件**。

### 它给出的权威事实（可直接采用）

- **`Loc`**：`Frontline = 7`，注释写明「前线是双方共享的一个格子，归属由第一张牌决定」
- **`Trigger`**：68 个触发器，值来自 UHT 头文件 `ERegisteredCardFunction.h`
- **`Kw`**：17 个关键字位（Guard/Blitz/Smokescreen/Ambush/Mobilize/HeavyArmor/
  Deployment/Veteran/Pinned/Suppressed/Fury/Covert/Bond/Develop/Forecast/Scrying/Salvage）
- **回合**：每回合槽位 +1、上限 **12**；克redit 重置为槽位数；
  **双方每回合都抽 1 张**；**手牌上限 9**，超出的抽牌直接烧进弃牌堆
- **疲劳**：牌库空 → 疲劳 +1 并对 HQ 造成该值伤害
- **攻击合法性**：`CanAttack` 要求 `!AttackedThisTurn && !SummonedThisTurn`，
  且非前线单位要 `Range >= SupportLineAttackRange`
- **Pinned / Suppressed** 在**该方回合结束时**清除
