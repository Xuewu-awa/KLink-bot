# 模拟器保真度对拍报告（第一次）

> 工具：`tools/BoardCompare`
> 数据：玩家真实对局 6 局，真实棋盘快照 250 条，动作 550 条
> 结论一句话：**卡牌数值 97%+ 对得上；已修掉三个 bug（指令牌被集体清空 / kredit 槽位机制缺失 / 工具自身没加载效果系统）；效果系统打开后准确率反而下降 —— 效果内核现在是最大的一块。**

## 0.0 ⚠️ 先纠正一个我自己的测量错误

`KismetLibrary.Initialize` **在整个 `src/KLink.Bot` 里没有任何调用点**，只有
`tools/BotSim/Program.cs` 调了。`BoardCompare` 第一版没调 → `KismetLibrary.Default`
是 `null` → **除手写脚本外的所有卡牌效果都不执行**。

后果：`Api.RunCardEffect` 会把每张这样的卡记成 `<card:X>` 未实现，看起来像
"这些卡缺实现"，实际是"整个效果系统没打开"。**本报告此前报出的所有数字，
都是在无效果引擎上测的。** 已修（现在 IR 加载 1636 张卡可解释）。

打开效果之后准确率**下降**了 —— 因为效果开始执行，而执行有错：

| 字段 | 效果关闭（错） | 效果打开（正确） |
|---|---|---|
| 卡名 | 97.8% | **97.4%** |
| 攻击力 | 98.7% | **87.7%** ← 掉了 11 个点 |
| 防御力 | 97.2% | **96.5%** |
| 区域 | 52.5% | **49.9%** |
| 动作应用 | 72.4% | **69.8%** |

**攻击力掉 11 个点是关键信号：加成/减益类效果正在被错误施加。**
这比"效果不执行"更值得查 —— 不执行只是少算，错误执行会把状态带偏。

## 0. 已修的三个 bug（2026-09-26）

### bug 1（严重）`CheckDeaths` 会把双方牌库里所有指令牌收进弃牌堆

`MatchEngine.CheckDeaths()` 遍历的是**所有卡**（`State.CardsUnordered()`），没有筛位置。
而指令牌（`Type=order`）的 `defense` 天然是 0 —— 于是**第一次**调用
（= 本局第一张牌被打出时 `PlayCard` 末尾那次）就把双方牌库 + 手牌里**全部指令牌**
一次性判死、扔进弃牌堆。

实测证据（match40 / replay-989040，act=4）：

```
act=1  区域 99%   真实 牌库=67 手牌=8    内核 牌库=69 手牌=9     ✓
act=3  区域 88%   真实 牌库=66 手牌=9    内核 牌库=68 手牌=10    ✓
act=4  区域 36%   真实 牌库=66 弃牌=1    内核 牌库=27 弃牌=50    ← 炸
```

内核弃牌堆里正好 **50** 张 = 该局 `defense<=0` 的指令牌 49 张 + 刚打出的那张。
（act=1 非 HQ 卡 75 张，其中 `defense<=0` 的 49 张，**全部是 Type=2 指令牌**。）

我一开始误判成 `card_event_pams` 这张牌的效果执行出错 —— 因为 act=4 正是它被打出。
实际上它只是这局第一张被打出的牌，**触发的是 `PlayCard` 尾巴上的 `CheckDeaths`**，
和它自己的效果无关（它的 IR 里根本没有弃牌操作）。

修法：加 `card.Location.IsBoard()` 限定 —— "阵亡"只适用于在场单位。

### bug 2 `NonZero` 没滤掉 `"None"`

`WireAction.NonZero` 过滤了 `null`/`""`/`"0"`，但动作数据里空槽位序列化出来是
**字面量 `"None"`**。漏掉它导致身份校验把合法动作判失败
（`卡组码 None 不在 deckCodeIDsTable2 里`，误杀 29~40 条 PC）。

修完之后指标没变好（区域 52.8%→52.5%）—— 因为这条只是**掩盖**了下一个问题：
那些动作现在能进到 `CanPlay`，然后卡在 **kredit 不足**上。

### ⚠️ 对已有训练数据的影响

**之前 1 万场自对弈的训练数据是带着 bug 1 生成的。** 那批数据里所有指令牌
在第一张牌打出后就被清空了，等于牌库退化成纯单位牌。所以：

- 「向量方案能学」这个结论仍然成立（74.3% 说明架构有效）；
- 但**那批数据不能代表 KARDS 的规则**，神经网络要重训。

### bug 3（kredit 记账）缺了「额外 kredit 槽位」机制 —— 已修

对拍发现真实玩家**一回合花掉的 kredit 超过上限**：

```
T11 left  上限 6: mi_5(3) + war_bonds(5) = 8
T14 right 上限 7: queens_own(7) + m2a4_bal(2) = 9
```

查卡面找到机制：

- `card_event_the_war_machine`（2 费）: "Gain **1 extra kredit slot**." → `GainKreditSlot`
- `card_event_war_bonds`（5 费）: "Gain **2 extra kredit slots**." → `GainKreditSlot`

共 **31 张牌**用这个调用。我的 `StartTurn` 只按回合数 +1，完全没算卡牌给的额外槽位，
所以后面的出牌被误判成 "kredit 不足" 而拒绝。

修完之后的实测轨迹（replay-989040，左侧）：

```
T3  上限 3   ← 回合数 2 + the_war_machine +1
T7  上限 6   ← 4 + 2（the_war_machine 第二次）
T9  上限 9   ← 5 + 2 + war_bonds 的 +2 槽位
T11 上限 10  → mi_5(3) 与 war_bonds(5) 均「应用」（此前两条都被拒）
```

⚠️ 还有一处没修完：`CardApiDispatch` 里 `GainKreditSlot` 把增量**硬编码成 1**
（`GainKreditSlot(SideArg(...), 1)`），而 `war_bonds` 是 +2。
上面的轨迹之所以对，是因为 IR 路径自己带了参数；但硬编码那条分支是错的。
另外 T14 右侧仍有 3 条被拒（queens_own 7 + m2a4_bal 2 + kettenkrad_home_bal 2 = 11
而右侧上限只有 7）—— 右侧这一局没拿过额外槽位，说明还有第三种降费/加费机制没找到。

## 1. 这个工具在干什么

拿玩家真打的一局，把服务器录下的动作流一条条灌进我的内核，**在每个真实快照点上把两边棋盘逐字段比一遍**。
产出的是准确率数字，不是"感觉差不多"。

两路数据来源**互相独立**，所以才能互为裁判：

| | 来源 | 是什么 |
|---|---|---|
| 真实棋盘 | UE4SS 注入客户端采的 `snapshot-match*.jsonl` | 客户端内存里 `CurrentSnapshot` 的全量卡牌状态 |
| 动作流 | fyserver 录的 `replay-<id>.actions.json` | 服务端权威动作记录 |

对齐方式：快照自带 `act`（= 客户端 `actionsCreated`，本地方已结算的动作数），
实测 **`act` 就是动作流的 `action_id`**，无偏移。

跑法：

```
dotnet run --project tools/BoardCompare -c Release           # 全部对拍
dotnet run --project tools/BoardCompare -c Release -- --only 989040 -v
```

## 2. 三个必须先定的口径（都是这次实测出来的，别再猜）

### 2.1 location 枚举

从快照实测反推，并用开局牌数自洽验证：

| 值 | 含义 | 开局数量 |
|---|---|---|
| 0 | 伪卡（sideeffect holder） | 2 |
| 1 / 2 | 左 / 右牌库 | 35 / 34 |
| 3 / 4 | 左 / 右手牌 | 4 / 5 |
| 5 / 6 | 左 / 右**半场**（HQ 也在这里） | 各 1（HQ） |
| 7 | 前线 | 0 |
| 8 | 弃牌堆 | 0 |

自洽性：左 4手+35库+1HQ = 40 ✓，右 5手+34库+1HQ = 40 ✓，合计 80 + 2 伪卡 = 82 ✓
（**HQ 本身是 40 张里的第 40 张**，所以是 39+1 而不是 40+1。）

### 2.2 `locationNumber` 是**分区内**索引，不是全局槽位

全量分布实测：牌库 0~38、手牌 0~8、半场 0~4、前线 0~3、弃牌堆 0~32。
所以跨分区比槽位没有意义，只在「双方都在前线」时才可比。

### 2.3 HQ 血量**不能**从快照取

`card_location_alam_el_halfa` 的 `defense` 在 act=1 / 60 / 129 三次采样**恒为 20**，
而这一局打了 34 回合。快照读的是卡面基础值，不是当前血量。
→ HQ 保真度只能取自动作流自带的 HQ 字段（结算前采样）。

## 3. 最大的一个坑：快照和回放的**左右是反的**

第一版跑出来卡名只有 40.1%。逐条看差异，发现：

```
[act=1] #1  卡名 真实 card_location_alam_el_halfa vs 内核 card_location_london
[act=1] #41 卡名 真实 card_location_london         vs 内核 card_location_alam_el_halfa
```

**两个 HQ 正好对调**，而且左方整套牌的编号整体偏移 40。

原因：采集快照是**本地客户端视角**，fyserver 回放是**服务端视角**，
"谁在左边"两边并不总是一致 —— 有的局一致，有的局反。

修法：用开局快照的卡名分布自动判方向（两种映射各数一遍命中，谁多听谁的），
映射规则是编号 ±40（1..40 ↔ 41..80）。**这是从数据本身读出来的，不猜。**

| 局 | 定向 |
|---|---|
| 206428 | 对调 |
| 634651 | 对调 |
| 590119 / 989040 / 641464 / 499982 | 一致 |

修完之后：卡名 40.1% → **97.8%**。

## 4.5 现在最大的问题：kredit 记账对不上

修掉 bug 1 之后，区域错配 TOP 变成：

```
真实 弃牌 → 内核 牌库   2733
真实 弃牌 → 内核 手牌   2166
真实 牌库 → 内核 手牌   1368
真实 牌库 → 内核 弃牌    931
```

`真实弃牌 → 内核牌库/手牌` 共约 4900 次（占 25%），和 **27.6% 动作被拒**吻合 ——
动作被拒 → 牌没动 → 卡在原地。

未应用动作分布（修 bug 2 之前）：

| 类型 | 条数 | 原因 |
|---|---|---|
| `PC` | 29~40 | **打不出：kredit 不足** |
| `CS` | 15 | 未处理的动作类型（还没解码） |
| `AC` | 7 | 身份冲突 |
| `ML` | 4 | 移动被拒（当前 HandRight）← 上游 PC 被拒的连锁 |

所以下一个要修的是 **kredit 记账**：内核算出来的可用 kredit 比真实少，
导致真实合法的出牌被判非法。这比指令牌那个 bug 更接近"规则错"。

另外 `CS` 这个动作类型至今没有映射 —— 从键位 `{"0":"73","1":"2","2":"pO"}`
看形状像"选牌"（HT 之外的第二类选择动作），需要从客户端行为反推。

## 5. 「区域 43.6%」的根因已经定位到**一张牌**

区域错配 TOP：

```
真实 牌库 → 内核 弃牌   875
真实 手牌 → 内核 弃牌   123
真实 牌库 → 内核 手牌    70
```

逐快照诊断（989040，这局卡名/攻防**全程 100%**）：

```
act=1  区域 99%   真实 牌库=67 手牌=8      内核 牌库=69 手牌=9    ✓
act=3  区域 88%   真实 牌库=66 手牌=9      内核 牌库=68 手牌=10   ✓
act=4  区域 36%   真实 牌库=66 弃牌=1 手牌=8
                  内核 牌库=27 弃牌=50 手牌=1   ← 41 张牌从牌库倒进弃牌堆
```

act=4 是哪条动作？动作流里是：

```json
{"action_id": 4, "action_type": "PC", "player_id": 385965,
 "action_data": {"0": "73", "4": "DT"}}
```

cardID 73 = **`card_event_pams`**（1 费英国指令）。

它的真实效果是：

> Develop a British order costing 4 or less. Add it to your deck with a cost of 0.

它的 IR 调用表：`GetDeckByside`、`GetCardFromID`、`MoveCardToTopOfOwnersDeck`、
`selectCardToDraw`、`RandomIntFromRangeWithStream`、`ChangeKreditCost`。

**我的内核执行这个程序时，把 41 张牌从牌库移进了弃牌堆。**
一个动作污染了之后所有快照 —— 这就是「区域」只有 43.6% 的全部原因，
也解释了为什么卡名/攻防还有 97%+（牌都还在，只是位置全错）。

这是典型的效果内核 bug（`GetDeckByside` 循环 + 派发解析），不是"模拟器整体不准"。

## 6. 下一步（按性价比排）

1. **修 kredit 记账**（这是现在最大的一块，约 25% 的区域错配来自它）。
   对内核算出的 `Kredits(side)` 与真实动作的合法性做逐回合对拍，找出从哪一回合开始偏。
2. **解码 `CS` 动作**（15 条）：形状像第二类"选牌"动作，需要从客户端行为反推。
3. **半场建模**：真实单位会停在 loc=5/6（半场/支援线），我的内核永远塞前线。
   战线 86.5% 就是这个差异。
4. **HQ 17.9%** 单独查：这条用的是动作流字段，和棋盘 bug 无关，是独立问题
   （而且修完 bug 1 之后它从 26.1% 掉到 17.9%，说明更多动作被真正执行后，
   内核的 HQ 轨迹偏离得更明显了）。
5. **重训神经网络**：现有 1 万场数据带 bug 1，必须重新生成。

## 7. 诚实的边界

- 只有 **6 局 / 250 条快照**，样本很小。玩家再多打几局，样本量上去结论才稳。
- `cardID` 我们只确认了 1..80 的对应关系；**局中生成的新卡（>80）没有可靠映射**，
  这部分被算进"内核缺 / 真实缺"里了。
- 每局有 3~4 张对手侧桩数据（`Name="None"`，全默认值），已排除，不参与比对。
- HQ 血量在快照里取不到，这一条目前只有动作流一个来源，没有第二路交叉验证。
