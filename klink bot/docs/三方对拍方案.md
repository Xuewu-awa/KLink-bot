# 三方对拍方案：真实牌局 × 我的内核 × kards-sim

> 目的：**给 kards-sim 一个它从来没有过的真实性数字**，同时**拿它当金标准来定位我内核的 bug**。
> 状态：侦察完成，方案确定，待实现。

---

## 1. 为什么可行

我已有的 `tools/BoardCompare` 干的就是这件事：「把真实动作一条条灌进引擎，
在每个真实快照点上逐字段比」。**把引擎换成 kards-sim**，同一套真实数据就能同时得到两个数字。

三方各自独立：

| | 是什么 | 可信度 |
|---|---|---|
| **真实** | UE4SS 注入客户端采的 `snapshot-match*.jsonl` | 地面真值 |
| **我的内核** | `src/KLink.Bot`，手写 IR 解释器 | 卡名 97.4% / 攻击 87.7% / 区域 49.9% |
| **kards-sim** | `ref/kards-sim`，Kismet AST 直译 | **从未与真实对局核对过** |

kards-sim 自称「自对弈 500 局 0 未实现调用 / 触发点 61/61 / 1638 张卡强制演练 0 异常」，
但这些**全是自洽性检查**，不是真实性检查。它跟真实游戏差多少，目前没人知道。

## 2. 已验证的技术前提

### 2.1 kards-sim 新版可编译、可编程驱动

- 新版：1714 个 `.cs` / 20.5 MB（旧 1705 / 18.9），`dotnet build ref\kards-sim\KardsSim\KardsSim.csproj -c Release` → **23.9 s / 0 错误**
- **我先前报的 3 个缺陷全部已修**（见 §4）
- 关键 API：
  ```csharp
  public GameEngine(int seed, string leftDeck = null, string rightDeck = null, bool log = false)
  public static GameEngine FromState(GameState s)     // ← 手工摆好状态再起引擎
  public bool Apply(GameAction a)                     // ← 逐动作重放入口
  ```
- `GameState` 的 `Left/Right.Deck/Hand/Board/Discard`、`Frontline`、`Hq/Kredits/KreditSlots/Fatigue`
  **全是 public 可变列表/字段** → 可以把状态摆成和真实开局一模一样。

### 2.2 开局牌库顺序可以完整还原（已实测）

`locationNumber` 在 **act=1** 时是干净的：手牌与牌库是**同一个 39 格数组**，
手牌占前 4（右侧 5）格。实测 snapshot-match40：

```
act=1  左库 35 张，编号 4..38，互不相同
       右手 5 张 + 右库 34 张，编号 0..38 连续
```

→ **按 `locationNumber` 排序即可还原真实初始牌序**，手牌 = 前 N 格，牌库 = 其余。

⚠️ **但局中不可信**：act=30 时左库出现四个编号 0；act=3 就消失了编号 21 而 4..20 仍在。
移动过的牌编号被重置为 0，顺序不再是排列。**所以只用它摆初始状态，不要用它跟踪位置。**

这一步的价值：**把「洗牌 / 抽牌」这个随机源彻底消掉**。
如果不还原初始牌序，抽到的牌就不一样，整局都会跟着偏，任何对拍数字都被这个噪声污染。

### 2.3 编号空间天然对齐

`GameState.NewCard` 顺序发号（`_nextId++`，从 1 起）。
真实编号是**左 1..40、右 41..80**，所以按 cardID 顺序建卡，ID 自动对上。
必要时也可以直接写 `Card.InstanceId`。

## 3. 实现步骤

新工具 `tools/TriCompare`（或扩展 `BoardCompare` 加 `--engine kardsim`）：

1. **读真实数据**：act=1 快照 + 全部快照 + fyserver 动作流（复用 `ReplayData`）。
2. **摆 kardsim 初始状态**：
   - `new GameState(seed, null, null, false)`（空牌库）
   - 按 cardID 顺序 `NewCard(def, owner)` 建 80 张 → ID 天然 = 1..80
   - 按 `locationNumber` 排序，前 4/5 张进 `Hand`，其余进 `Deck`
   - `Hq = 20`，`Current = Left`，`Turn = 1`
   - `GameEngine.FromState(S)`
3. **摆我的内核初始状态**：`ReplayRunner.InitialLocations`（已实现，但要改成用 `locationNumber` 还原**顺序**，现在只是分区）。
4. **逐步灌真实动作**，在每条真实快照的 act 上，对**两个引擎**各比一次同样的字段：
   卡名 / 攻击 / 防御 / 所在区域 / 战线（半场 vs 前线）/ 关键词 / HQ。
5. **输出**：
   - 两个引擎各自 vs 真实的准确率表（kards-sim 的第一份真实性数字）
   - **分歧清单**：真实与 kards-sim 一致、但与我不同的位置 → 这些就是我的 bug，
     而且可以直接去 kards-sim 读对应实现（它是逐条转译，能直接看到客户端原本怎么做）

## 4. 附带发现（可以反馈给作者）

1. **`Rules.DeckSize = 30`，但实测每方 40 张**
   （`Core/GameState.cs`：`public const int DeckSize = 30;`，注释写「已与客户端一致：NumCardsInDeck=30」）
   我从真实抓包量到的是：左手 4 + 左库 35 + 左 HQ 1 = 40，右手 5 + 右库 34 + 右 HQ 1 = 40，
   加 2 张伪卡（sideeffect holder）共 82 —— 与快照的 `count=82` 完全自洽。
   构造赛每方是 40 张。这个常量如果是给自对弈用的，可能与真实规则不符。

2. **他们「已知未完成」里要的东西我正好有**
   > 接官服需要一个**真实玩家的对局抓包**才能对齐「客户端权威」的边界
   我这边有 6 局真实对局 / 250 条逐卡棋盘快照 / 550 条动作流，
   而且已经证明 `act == action_id` 精确对齐、`locationNumber` 可还原开局牌序。
   可以导成干净格式给他。

3. **他们文档里的方法论我该抄**
   - 「#12 未实现调用静默变成 0 —— 容错设计本身是最大的错误源」→ 让容错**可观测**：
     未实现登记 + `smoke` 把未实现当**失败**返回非零。
     我上一轮把「效果系统压根没加载」误读成「这些卡缺实现」，正是缺这道断言。
   - 「#11 静态覆盖会说谎」→ 他们的 `smoke` = **逐卡强制触发每一个触发点**，绕开随机采样。
     我只有对拍，没有这个：随机对局抽不到的卡等于没测。
   - 「#9 `a[0]` 是接收者，实参从 `a[1]` 起」
     → 我审计了自己的 IR：15290 个 call 里 **1420 个 `args[0]` 是 self 占位**，
     29 个函数两种约定混用（`ChangeAttack` 143/285、`ChangeDefense` 76/267 …）。
     我在 VM 里加了摘除占位的修正，**但重跑数字一模一样，所以这条线索还没证实** ——
     不能声称它解释了攻击力那 11 个点。
