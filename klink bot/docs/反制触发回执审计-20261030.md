# 反制触发通知及本地手牌刷新

本批修复一条共享规则链：`GotchaTriggered` 原来省略了通知，也因此没有模拟通知接收端的延迟手牌重排。现在先记录 `ZActionGotchaTriggered`，随后执行 T21 观察者；本地动作结算回执只重新查询卡牌当前阵营并压紧对应手牌，不重复执行反制效果。

## 权威依据与边界

依据原始解析字节码，不使用旧回放作为规则依据。完整提取函数、文件 SHA-256、DeepSeek 机械提取的逐条复核和版本比较见 [机器记录](../../out/audit/systematic-rules/countermeasure-receipts-20261030.json)。

- `BP_CardFunctions.GotchaTriggered`：i=141 直接写弃牌区，i=243 整理手牌，i=525 通知，i=610 起查询 T21 接收者，i=879 调用观察者；i=1008 后才处理停止标志与 `cancelOrderRemove`。不能因为参数名 `skipDiscardingOrder` 就把指令移回手牌。
- `U_CardFunctionsNotifier.NotifyGotchaTriggered` 转发到 OnlineMatch；`AddSubActionGotchaTriggered` 只构造 `cardID`、`instigatorID`、`StopCard` 三字段，不包含 `cancelOrderRemove`。
- `BP_OnlineMatch.ReceiveActionGotchaTriggered`：本地 i=525 分支跳过触发函数，i=539 查询当前卡对象，i=593 获取当前阵营手牌位置，i=669 重排。远端重建分支不在本批实现范围。
- 非正 ID 查询返回空对象，空上下文的阵营零值经 `GetHandLocationBySide` 映射到右方手牌；使用已有查询 API 保留该边界。
- 棋盘读取 `cancelOrderRemove` 字段是否存在，传给手牌/选择卡预览 Actor 的 `cancelRemove` 参数。已检查的写入和读取不能支持“该标记让指令逻辑上留在手中”的解释；不对 UI 全闭包作认证。

CardFunctions、Notifier、Board、HandCard、ChooseOneCard 的旧提取与新版 FModel 导出共十个 uasset/uexp 文件逐字节一致。新版 OnlineMatch 已重新解析；本批五个相关函数的 bytecode、function_flags、expression_count 与旧解析一致，未把整个资产认定为相同。DeepSeek 交付五处标记出现位置，主 agent 对原始语句、位置和全部调用列表独立逐条核验通过。

## 回归与验证

新两项回归在修改生产代码前均失败，分别报告缺少触发通知、缺少延迟手牌刷新。修复后覆盖：双侧八种 stop/skip 组合、真实 THE TIGERS 的 T21 增益与通知先后、真实 ULTRA 双侧根动作取消 WAR BONDS 并给反制方抽牌，以及六种当前阵营/非正 ID 延迟刷新场景。重复消费回执不重跑效果。

完整 1033 项 BotSim、49 项动作数据、31 项动作模型及 16 项矩阵检查通过。前三类检查日志及哈希记录在机器报告；完整 BotSim 使用独立构建工作树，避免纳入主工作树原有的无关 IsolatedActionProbe 修改。生产源与新增测试从主工作树复制，未提交独立工作树内其他改动。

## 仍开放

发现另一条明确遗漏：`NotifyStopFurtherActions → BP_OnlineMatch.StopFurtherActions` 会给当前累积的 `ZActionPlayCardFromHand` 通知追加 `actionCancelled=1`，模拟器尚未实现该通知改写。它涉及动作批次边界及嵌套自动出牌，本批没有混入未经核验的全历史日志改写；下一批优先处理。

远端回执、完整取消批次、重入生命周期、选择组合及逐卡认证仍开放。本批不建立完整 PvP 还原或可靠合法动作掩码的结论。
