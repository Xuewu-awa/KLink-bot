# 效果内核验证报告

> 记录「用真实对局反推内核正确性」这条链路上已经抓到的问题、修法与证据。
> 相关代码：`src/KLink.Bot/Effects/`、`src/KLink.Bot/Replay/`、`tools/BotSim/SelfTest.cs`

## 1. 验证手段有两层

| 层次 | 命令 | 能回答什么 |
|---|---|---|
| **单卡断言** | `dotnet run --project tools/BotSim -- selftest` | 某个原语/某张卡的效果**本身**对不对（最小可复现） |
| **整局对拍** | `dotnet run --project tools/BotSim -- replay --match <id>` | 规则理解在**真实对局里**对不对（逐步比对手方 HQ 防御） |

两层缺一不可：整局对拍只能告诉你「第几步对不上」，
常常分不清是「效果没触发」「原语接错参数」还是「前置条件不满足」；
单卡断言能把这三者区分开。

## 2. 已修的问题

### 2.1 ⭐ `GetOppositeSide` 没有入参，内核却按入参读

**症状**：`card_unit_10_5_cm_lefh`（10.5cm leFH，「Deployment: 对敌方 HQ 造成 2 点伤害」）
完全不生效。

**证据**（`tools/analyze-call-arity.py`）：扫描全部 2053 张卡的 Kismet 字节码，
`GetOppositeSide` 出现 **756 次，每一次的参数表都只有 1 项**，
而且那一项是 out 槽 `CallFunc_GetOppositeSide_oppositeSide`。
对照：`GetLocationCardBySide` 3 项、`GetCardsOnBoardBySide` 4 项 —— 入参都老实列着。

```text
GetOppositeSide            参数 1 个 ×756   例: CallFunc_GetOppositeSide_oppositeSide
GetLocationCardBySide      参数 3 个 ×307   例: card, locationCardID, InstanceVariable
GetCardsOnBoardBySide      参数 4 个 ×298   例: oppositeSide, False, False, cards
```

所以「我方」只能取自卡自己，不是参数。

**修法**：`CardApiDispatch` 里改用 `SelfSide(c)`（`Self.Owner`，退回 `Controller`）。

**影响面**：**463 张卡**用到它，是第 3 常用的外部调用（仅次于 `IsLocatedOnBoard` / `IsUnit`）。
旧实现读到未赋值的 out 槽 → `Side.NotAvailable` → 后续 `GetLocationCardBySide` 返回 null
→ 整条链**静默失效**。

### 2.2 ⭐ `TargetCard` 把「接收者」当成「目标」—— 所有显式指定目标的原语都打在施法者自己身上

**症状**：lefh 的战吼把**自己**的防御从 3 打到 1，敌方 HQ 纹丝不动。

**证据**（原始字节码）：

```text
DamageCard(
  [0] LocalVariable   CallFunc_GetLocationCardBySide_card   ← 目标（敌方 HQ）
  [1] IntConst        2                                      ← 伤害
  [2] InstanceVariable cardID                                ← 来源，不是目标
  [3..5] False
  [6] LocalVariable   CallFunc_DamageCard_targetDestroyed
)
```

这类原语在字节码里的形状是
`Context{cardFunction}.DamageCard(目标, 数值, 来源, …)` ——
**接收者是 `cardFunction`（施法者自己）**，真正的目标在 `Parameters[0]`。
旧实现写成 `AsCard(receiver) ?? args…`，于是先命中了自己。

**修法**：`TargetCard` 改成**先扫参数、再看接收者**：

```csharp
foreach (var v in args)
    if (AsCard(v) is { } explicitTarget) return explicitTarget;
return AsCard(receiver) ?? c.Target ?? c.Self;
```

`Parameters[0]` 也可能是 `InstanceVariable cardID`（自我引用），
那时 `AsCard` 取不到卡、自然回退到接收者 —— 行为正确。

**影响面**：`DamageCard` / `ChangeAttack` / `ChangeDefense` / `DestroyCard` /
`HealCard` / `ChangeKreditCost` / `ChangeOperationCost` … 全部。

### 2.3 另外两个「零入参却被当有入参」的原语

`getTotalAttack` / `getTotalDefense` 同样是零入参（自己的场面总值），
旧实现 `SideArg(r, a, 0)` 退化成 `NotAvailable` → **恒返回 0**。

`tools/check-zero-input-dispatch.py` 会交叉比对字节码与派发表，自动找出这一类。
当前结果：**只剩这 2 个**（已修）。

## 3. ⚠️ 还没修的大缺口：`ctx` 限定的成员读取被忽略

**这一条影响面最大，是下一步的重点。**

IR 里有这种表达式：

```json
{
  "op": "set",
  "dst": "CallFunc_EqualEqual_ByteByte_ReturnValue",
  "src": { "math": "EqualEqual_ByteByte", "args": [
      { "var": "side", "ctx": { "var": "K2Node_Event_attackerCard" } },
      { "var": "side" }
  ]}
}
```

意思是 `攻击者卡.side == 我这一侧` —— 也就是
`card_unit_3_panzergrenadier`（「Gets +1+1 after **you** operate a German unit」）
的**阵营守卫**。

但 `KismetVm.Frame` 没有实现 `ctx`，`Eval` 直接当成普通局部变量读 →
两边都是 `ctx.Controller` → **`side == side` 恒为真，守卫永远不拦**。

**症状**：310284 里 `3_panzergrenadier#36` 在 T10 已经涨到 **12/9**（基础 3/3），
因为**对手**每次行动它也跟着 +1+1。

**规模**（扫描 `docs/card-ir.json`）：

| 指标 | 数值 |
|---|---|
| IR 总步数 | 55,225 |
| 含 `ctx` 限定的步数 | **3,748** |
| 涉及卡数 | **1,045**（约一半） |

读得最多的成员：`cardID`(881)、`side`(610)、`name`(230)、`faction`(109) ——
**全是守卫/过滤用的字段**，所以「守卫恒真」是系统性的，不是个例。

涉及的上下文变量（事件变量）：

```text
CallFunc_Array_Get_Item            459      K2Node_Event_cardDestroyed    71
K2Node_Event_cardPlayed            230      CallFunc_GetRandomCard_randomCard  60
K2Node_Event_targetCard            188      K2Node_Event_cardLeaving      39
tempCard                           176      K2Node_Event_cardMoved        26
CallFunc_GetCardFromID_card         89
```

**修法**（三件事，缺一不可）：

1. `KismetExpr` 暴露 `Ctx`；`Eval` 遇到 `ctx` 时先把 `ctx` 求值成一张卡，
   再读它的成员（`side`/`faction`/`name`/`cardID`/`location`/`attack`/`defense`…）
2. `Frame` 增加事件变量绑定；`CardApi.FireTrigger` / `RunTriggerProgram`
   在派发时把事件主体绑到对应的事件变量名上
3. 成员读取要能穿透 `CallFunc_Array_Get_Item` 这类「局部变量里存着一张卡」的情况

修完必须重跑 `selftest` + 5 局回放，确认 310284 的 HQ 轨迹能越过第 9 回合。

**310284 目前唯一未解释的偏差**：
A35 `AC 7_schutzen 打 m16_halftrack` 之后左方 HQ 18 → 15（**多出 3 点**）。

「动作流漏记了一条」是当前最可能的解释。

## 5. 复现方式

```powershell
# 单卡效果断言
dotnet run --project tools/BotSim -c Release -- selftest

# 整局对拍（--stack 打堆栈）
dotnet run --project tools/BotSim -c Release -- replay --match 310284

# 自对弈回归（看异常/未实现调用）
dotnet run --project tools/BotSim -c Release -- play --games 200
```

用来做证据提取的一次性脚本（都在 `klink bot/tools/`）：

| 脚本 | 作用 |
|---|---|
| `analyze-call-arity.py` | 统计每个原语的参数表形状，找「零入参」原语 |
| `check-zero-input-dispatch.py` | 交叉比对字节码与派发表，列出读错参数入口 |
| `check-id-semantics.py` | 校验快照 cardID ↔ 动作自带卡组码是否一致 |
| `check-card-zones.py` | 校验「打出的牌在快照里到底算手牌还是牌库」 |
| `show-extra-fields.py` | 打印每局那个「额外状态字段」的取值轨迹 |
| `decode-action-ids.py` | 把动作流里每个 cardID 的全部用法 + 牌码翻出来 |
