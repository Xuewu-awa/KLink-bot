## 6. 出牌结算流程（`ReceiveActionXActionPlayCardFromHand` 原文）

```
1. AddActionEnd(subActions)
2. DoSubActions(subActions, receiveFromLocal, out visualActions)
3. AddActionToVisualQueue("XActionPlayCardFromHand", actionData, visualActions)
```

`receiveFromLocal` 对应 CDO 字段 `ResolveSubActionsFromLocal`；配合 `server_options.skip_sending_subactions = 1`，
本 build 下效果由双方客户端各自本地计算（**确定性锁步**）。

## 8. ⭐ 线上实测校正（真实客户端动作）

数据来源：`tools/extract-live-actions.py` 从 fyserver 控制台日志抽出的 8 条解密动作，存于 `docs/live-actions.json`。

### 8.1 `action_type` 在网络上走**紧凑名**

前几节从蓝图字符串常量推出的名字（`XActionPlayCardFromHand` 等）是**全名**，
但真实客户端发的是紧凑形式 —— 对应 CDO 里的 `XActionNamesFullToCompact`
与 `server_options.feature_compact_action_values_only_enabled = 1`。

| 全名（离线推断） | 线上实际（实测） |
|---|---|
| `XActionPlayCardFromHand` | **`PC`** |
| `XActionMoveCardToLine` | **`ML`** |
| `XActionAttackCard` | **`AC`** |
| `XActionStartOfTurn` | `XActionStartOfTurn`（不压缩） |
| `XActionEndOfTurn` | `XActionEndOfTurn`（不压缩） |

⚠️ 只有**主动操作**被压缩，回合边界动作保持全名。

### 8.2 `action_data` 用**数字下标**，不是名字

```
{"action_type":"PC","player_id":892257,"action_id":49,"local_subactions":1,
 "action_data":{"0":"64","1":"3","2":"0","3":"0","4":"jJ","84":"11"}}

{"action_type":"AC","player_id":654612,"action_id":39,"local_subactions":1,
 "action_data":{"0":"7","1":"59","2":"4H","3":"d3","84":"3"}}

{"action_type":"ML","player_id":892257,"action_id":50,"local_subactions":1,
 "action_data":{"0":"74","1":"1","2":"yD","84":"11"}}
```

前几节里 `ActionValue2.Name` 在线路上是**下标字符串**，
而且**含义随动作类型而变**（每种动作有自己的参数表，压缩后下标自然不同）：

| 动作 | `0` | `1` | `2` | `3` | `4` | `HQ*` |
|---|---|---|---|---|---|---|
| `PC` 出牌 | 卡牌 ID | **部署槽位** | 目标卡 ID | 0 | **卡组码** | 对手 HQ |
| `AC` 攻击 | 攻击者 ID | **防御者 ID** | **攻击者码** | **防御者码** | — | 对手 HQ |
| `ML` 移动 | 卡牌 ID | **目标槽位** | **卡组码** | — | — | 对手 HQ |
| `XActionStartOfTurn` / `XActionEndOfTurn` | — | — | — | — | — | 对手 HQ + `side` |

另外回放接口还会补一个 **`turn_number`**（真实客户端发的紧凑动作里没有），
回放驱动必须用它、不要自己数回合。

### 8.2.1 ⭐ `HQ*` 是**行动方对手**的 HQ 当前防御力（动作结算**前**采样）

> ⚠️ **早期版本这里写的是「行动方自己的 HQ」，是错的。** 用 5 局完整回放复核后改正。

判据一（310284，21 回合 / 94 条动作）：把该字段解释成**对手**的 HQ，
整条轨迹与终局完全闭合：

```
该字段取值（按行动方交替）:
  左方动作时（→ 看右方 HQ）: 20 … 20 17 15 12 10 8 5 3
  右方动作时（→ 看左方 HQ）: 20 18 … 15 11
最后一条动作: ActionEndMatch{ reason: Victory_DestroyHQ, winner_side: left }
             前一条: PC ace_of_spades 目标 41（右方 HQ），把 3 → 0
```

按「自己的 HQ」解释则终局时右方还剩 11 点，与 `Victory_DestroyHQ` 直接矛盾。

判据二（165924，独立复核）：

```
A16 AC 右方 2002 打 cardID 1（左方 HQ）   该字段 = 18
A17 AC 右方 2002 打 cardID 1（左方 HQ）   该字段 = 9
A18 ActionEndMatch{ Victory_DestroyHQ, winner_side: right }
→ 20 →(A15 战吼 2 点)→ 18 →(A16 打 9)→ 9 →(A17 打 9)→ 0  ✅ 闭合
```

两条推论：
1. **HQ 初始防御 = 20** —— 与 fyserver 注入的 bot 动作 `{"75":"20"}` 相互印证
2. **动作流自带一个关键状态量**，所以「喂动作流进内核、逐帧比对 HQ」就是一条
   现成的、可证伪的验证路径 —— 不需要额外的状态导出。
   实现对拍在 `tools/BotSim replay --match <id>`。

### 8.2.1.1 ⚠️ 这个下标**每局都不一样**，不能写死

`action_data` 是「下标 → 值」，而下标来自一张**动态登记**的字段名表，
所以同一个「对手 HQ」字段在 5 局里占了 5 个不同下标：

| 对局 | 310284 | 165924 | 955337 | 130691 | 563868 |
|---|---|---|---|---|---|
| HQ 字段下标 | `84` | `24` | `37` | `91` | `68` |

**动作参数 `0`..`4` 倒是全局稳定的**，只有这些「额外状态字段」的下标会变。
推断规则（`ReplayData.InferHqKey`）：键名是纯数字、不是 `0`..`4`、
出现次数最多、且首个取值是 20。

### 8.2.3.1 ✅ `card_id` 编号空间：左侧 1..40 / 右侧 41..80，且 = 卡组位次

`GetCardsFromDeck` 在**洗牌之前**按卡组码顺序发号：左方 HQ=1、卡组 2..40；
右方 HQ=41、卡组 42..80。所以 **`card_id` 就是「卡组里的第几张」**，
而 `location_number` 是洗牌后的位置。

对拍结论：动作自带的卡组码解析出的卡名，与快照里同 `cardID` 的卡名
**5 局零冲突**（`tools/check-id-semantics.py`）。所以**快照的 `cardID` → 卡名映射可信**。

### 8.2.4 ⚠️ 快照的**手牌/牌库归属不可信**

`MatchManagerService.GetCardsFromDeck` 是这样发的：

```csharp
cards = [.. cards.OrderBy(_ => Random.Shared.Next())…];   // 用 Random.Shared 洗牌
// 然后 MakeMatchStartingInfo:
match.LeftHand = leftCards.Take(4)…;                       // 手牌 = 洗牌后前 4 张
match.LeftDeck = leftCards.Skip(4)…;                       // 牌库 = 其余
```

但真实客户端**并不按它发牌**：实测 30 次 `PC` 里有 27 次打出的牌，
按快照判定都在**牌库**里（`tools/check-card-zones.py`）。
所以快照只能当**卡池**用，不能当「谁在哪」用。

要拿到客户端真实手牌，只有两条路：
1. 让 fyserver 把发给客户端的 `StartingData` 和收到的
   `POST /matches/v2/{id}/mulligan` 请求体（里面是客户端真实手牌里的 cardID）
   记下来，再打一局
2. 接受这个缺口，回放时「按需把牌注入手牌」（当前 `ReplayRunner` 的做法，会计数）

### 8.2.5 ⭐ `XActionCheat` 暴露了客户端的调试作弊面

```
{"0":"SetKredits","1":"right","2":"12","playerID":654612}
{"0":"SpawnCard","1":"right","2":"dy","3":"Hand_Right","4":"0","playerID":654612}
```

- `0` = 作弊命令名（`SetKredits` / `SpawnCard`）
- `1` = 目标阵营（`left`/`right`）
- `2` = 参数（`SetKredits` 是数值；`SpawnCard` 是**卡组码**）
- `3` = 目标区域（`Hand_Right` —— 直接印证了区域名映射）

所以 165924 / 955337 这两局是**开作弊打的测试局**，里面的
「kredit 不足」不是规则错误。这一条对将来自己驱动客户端很有用。

### 8.2.6 动作流里会有**重复记录**

310284 里 A73..A76 是**四条完全相同的** `PC{0:73, 1:3, 4:wM}`，
而 cardID 73 在快照里只有一张。回放驱动必须去重（当前按
「该 cardID 已在场 / 已打出过」丢弃，310284 共丢 11 条）。

### 8.3 `sub_actions` 确实是空的 —— 锁步模型得到确证

日志里每条动作的 `local_subactions` 都是 `1`，服务端侧的 `sub_actions` 是空数组。
**效果由双方客户端各自本地计算，不上网络** —— 与第 6 节的推断一致。

这也是为什么规则内核必须自己实现全部效果：服务端从头到尾看不到效果数据。

### 8.4 ⭐ 回放对拍已经抓出来的规则订正

用 310284（21 回合）逐帧对拍内核，抓出并修掉：

| 订正 | 原（错）理解 | 证据 |
|---|---|---|
| **没有召唤失调** | 打出当回合不能行动 | A24 `PC 77` → A25 `ML 77` → A26 `AC 77` 同回合；A34 `PC 65` → A35 `AC 65` 同回合 |
| **移动与攻击是两笔额度** | 共用一个 `OperationsUsedThisTurn` | 同上：先 `ML` 再 `AC` 不该被拒 |
| **回合只开一次** | 驱动既调 `EndTurn` 又调 `StartOfTurn`，kredit 上限翻倍 | 修前 T8 右方上限 8，实际 4 |
| **牌库要用分侧枚举** | 用了 `CardLocation.Deck` 而非 `DeckOf()` | 表现为每回合凭空吃疲劳：HQ 20→19→17→14→10→5 |
| **`Api` 必须在构造函数里建** | `Api` 只在 `Start()` 里赋值，回放不调 `Start()` | 回放路径上每个动作都 NRE |

订正后 310284：动作应用率 1.1% → **83.2%**，
HQ 轨迹干净到 **第 9 回合**（共 21 回合有采样）。

**当前唯一未解释的偏差**：
310284 A35 `AC 7_schutzen 打 m16_halftrack` 之后左方 HQ 18 → 15（**多出 3 点**），
是整局唯一一处无法用已知效果解释的 HQ 变化。
