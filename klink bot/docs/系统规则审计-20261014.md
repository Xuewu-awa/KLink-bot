## RULE-001：反制触发条件缺失（已修复）

客户端原生入口 RVA `0x4a85b20` 调用实现 RVA `0x4b0ddd0`。旧模拟器将条件简化为反制类型、存活和禁用标签，并且派发表丢弃了 `triggerCard` 参数。当前客户端的分支要求：

1. 若触发卡 `hasCovert=true` 且 `isRevealed=false`，反制接收者必须有 `customName1` 的 `canTargetCovert` 标记。
2. 接收者 `gotchaActivated > 0`，位于手牌位置 3 或 4，当前行动方与接收者阵营不同。
3. 接收者阵营没有 `sideeffect.blockgotcha`。
4. `GetAllCards` 返回的战斗卡中没有存在 `stop_gotcha` JSON 字段的卡；检查的是字段存在性，即使值为 false 也会阻止。

调用映射由当前内存中的 FName 常量确认：RVA `0x93abf68` 为 `GetPlayingSide`，`0x93abdf8` 为 `DoesSideEffectTagExist`，`0x93abe58` 为 `GetAllCards`。当前 pak 的 `GetAllCards` 调用 `GetAllCardInBattle`，不会按棋盘位置过滤。阻止后的 `NotifySideEffectTrigger` 只显示通知，按用户指定的无头范围省略。

字段偏移由当前 SDK 核对：`hasCovert +0x1ea`、`Location +0x275`、`side +0x276`、`gotchaActivated +0x308`、`isRevealed +0x33b`、`customJson +0x518`、`cardFunction +0x550`。JSON 辅助函数 RVA `0x4518400 -> 0x4518310` 核查的是字段存在性。

当前执行程序 SHA-256：`09df6b669944d5ca68f5b56741c05f591c03bfd3600f75829364a3452e661dc0`。已把入口、实现和三个相关辅助函数的内存字节与安装 PE 对比，5 / 5 完全一致。原生实现的 454 字节 SHA-256 为 `8c2303e30b79e99a74dbe388b8788d664e03f9090bd59462dd79cd4c517859dc`。本机采集记录为 `kards-install-review/gotcha-rule-evidence-20261014.json`。

IR 中 52 个卡条目调用此规则；修复共享原语与参数派发即可覆盖它们对应的调用。这个数字不是已经逐卡完整验证的数量。

验证：Release 的 `BotSim selftest` 293 / 293 通过。增加未装填、己方回合、牌库位置、未揭示隐蔽卡、许可标记、揭示后恢复、弃牌中 `stop_gotcha=false` 仍阻止以及删除字段后恢复的断言。旧攻击用例原先把反制卡放在支援线且未装填，现按客户端规则设置为手牌中的已装填卡。

## RULE-002：被抑制的 No. 3 Commando 仍禁止攻击（已修复）

当前 pak 的 `cardsCheckFunctions.CanOtherCardBeTargetted` 在语句 59 调用 `BP_GameState_Battle.FetchAllCardsWithEventTrigger(T2)`。公共查询在语句 682 读取接收者实例的 `suppressionExceptionTriggers`，语句 793 计算 `isSuppressed && !exception`，语句 853/867 跳过该接收者；位置过滤由接收者自身函数处理。

旧模拟器直接枚举双方棋盘与弃牌，并以存在同名函数判断订阅资格，遗漏公共查询的抑制过滤。结果是 No. 3 Commando 被抑制后仍可拒绝总攻至少 4 的单位攻击。现通过静态注册数组筛选订阅者并应用相同的抑制例外条件，再执行卡自己的函数；遍历范围也改为全局战斗卡快照。

回归使用 A-26 Invader、No. 3 Commando 和实际 infantry 目标，覆盖门查询、合法目标枚举和真正攻击；抑制后应放行，显式加入 T2 抑制例外时仍否决。新用例在修复前失败，修复后 Release 自测 293 / 293 通过。

公共抑制例外判定也移除了旧的 11 卡硬编码补丁，统一使用实例数组。当前完整 CDO 数据有 12 张卡具有非空例外数组；已逐卡读取 2,019 张卡的两个 uint8 枚举数组，4,038 / 4,038 与模拟器数据一致，读取错误为 0。额外断言验证卡牌原有的例外能生效、清空实例例外后不会继续因卡名被放行。

## RULE-003：全局卡枚举与同编号重排误用 CardId 排序（已修复）

当前 pak 的 `BP_GameState_Battle.GetAllCardInBattle` 在语句 11 对 `AllCardsInBattle` 调用 `Map_Values`，没有按 CardId 排序。`SortCardsByLocationNumber` 使用语句 611 的严格 `Greater_IntInt` 做稳定插入排序，相同位置编号保留输入先后。`BP_CardFunctions.RearrangeLocation` 在语句 10 调用排序查询，在语句 336 更新卡的位置与编号。

旧模拟器的 `GetAllCards` 与 `RearrangeLocation` 都以按 CardId 升序的 `State.AllCards` 为输入，丢失真实入表历史。现独立记录入表顺序，供这两个入口使用；状态快照也记录 `BattleCardOrder`。回归以先创建 ID 99、再创建 ID 10 且位置编号相同的两张卡验证：枚举应为 99、10，重排后位置编号分别为 0、1。

这项修复覆盖正常新增且没有删除、稀疏插槽复用的 map 路径。客户端 map/set 删除、再插入及运行时触发注册变更仍未完整验证；触发派发仍不能因此宣称与所有 UE TSet 顺序相同。其它查询入口也需要单独核查，未统一改变 `State.AllCards`。
