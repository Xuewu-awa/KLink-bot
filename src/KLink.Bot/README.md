## 核心思路：不手写效果，**解释 Blueprint 字节码**

原计划是给每张卡手写一段 C# 效果脚本 —— 267 张 × 每张几十行，慢且易错。

但完整字节码里天然带着数据流：

```
{"Inst":"Let","Variable":{"Variable Name":"tempCard"},
 "Expression":{"Variable Name":"CallFunc_GetLocationCardBySide_card"}}
```

`CallFunc_<函数名>_<参数名>` 就是那个调用的输出槽。配合 `JumpIfNot` 的控制流，
一张卡的效果就是「一串有输入输出的步骤」，可以直接解释执行。

于是分成两层：

| 层 | 文件 | 作用 |
|---|---|---|
| **原语层** | `Effects/CardApi.cs` + `CardApiDispatch.cs` | 那 170+ 个游戏调用的实现 |
| **编排层** | `Effects/Blueprint/KismetVm.cs` | 解释 IR，把原语按蓝图逻辑串起来 |

**覆盖率随原语层完善自动提升**，不需要为每张卡写代码。

### IR 从哪来

```
pak 里的卡牌蓝图 (.uasset/.uexp)
   ↓ UAssetCLI dump-batch --full        反编译 Kismet → JSON
cards.full.json (84 MB)
   ↓ tools/gen-kismet-ir.py             压成可解释的 IR
card-ir.json (19 MB, 1636 张卡 / 3608 个事件程序)
   ↓ KismetVm                           运行时解释
```

**两条已验证的关键事实**：

1. 事件 stub 里的 `ExecuteUbergraph_X(<entry>)` 实参，**正好等于** ubergraph 中
   该事件链第一条语句的 `StatementIndex` —— 1636 张卡全部命中
2. 局部变量名 `CallFunc_<函数名>_<参数名>` 标识调用的输出槽，数据流由此还原

参数形状也不是猜的：`tools/analyze-call-shapes.py` 从全部 35,360 个调用点
统计出每个调用的实际参数位置（例如 `ChangeDefense(target, instigatorID, 数值, …)`
里数值恒在 index 2）。

## 显式会话预备策略（RULE-237）

`GameState.CardReservations` 默认是 null，保持 CDO-only 兼容模式。要模拟某次服务器调档，需显式加载所选会话快照；仓库提供的 `card-reservation-session-20261019.json` 仅对应其记录的客户端版本与采集时刻，不是所有会话的默认配置。BotSim 构建会将该文件复制到输出目录的 Data 文件夹。

```csharp
engine.State.CardReservations = CardReservationPolicy.Load(
    Path.Combine(AppContext.BaseDirectory, "Data", "card-reservation-session-20261019.json"));

// 使用模拟器自己的服务器时间推进，不读取本机墙钟。
engine.State.CardReservations = engine.State.CardReservations
    .WithServerUtcTicks(nextSimulatedServerUtcTicks);

// 返回原有 CDO-only 兼容模式。
engine.State.CardReservations = null;
```

加载文件只构造不可变策略，赋给某局状态后才生效。策略或时间替换会清空该局相关的静态候选及开发候选缓存。也可直接用 `CardReservationChange`、`CardReservationPolicy` 构造来自其他已验证会话的数据；自动采集/刷新、完整配置与时钟链尚未接入；显式黑名单见下节。


## 显式会话黑名单（RULE-238）

`GameState.CardBlacklist` 默认是 null，保留空黑名单兼容模式。下面的可选文件来自实际 `BP_Logic.blacklistedCards` 映射，不假定任意服务器数组都能直接充当最终映射。

```csharp
engine.State.CardBlacklist = CardBlacklistPolicy.Load(
    Path.Combine(AppContext.BaseDirectory, "Data", "card-blacklist-session-20261019.json"));

engine.State.CardBlacklist = engine.State.CardBlacklist
    .WithServerUtcTicks(nextSimulatedServerUtcTicks);
if (engine.State.CardReservations is { } reservations)
    engine.State.CardReservations = reservations.WithServerUtcTicks(nextSimulatedServerUtcTicks);
```

同一会话的两份策略应使用一致的模拟服务器时间，加载不同采集时刻的快照后也应显式对齐时间。截止时刻仍在黑名单内，超过截止值才解除；`includeReserved=true` 不会绕过黑名单。替换策略或时间会使相关候选缓存失效；设为 null 恢复空黑名单。文件是有日期和版本范围的可选快照，不是所有对局的默认规则。会话条目合并见下节；黑名单键已接入成功转换的符号身份，自动采集和刷新生命周期仍待实现。


## 合并会话黑名单条目（RULE-239 / RULE-244）

可以显式应用有效且已连接分支的原始服务端 card_type 记录。接口只更新传入键，同名末项覆盖前项，过期值仍保存；空数组不清空旧映射。它与加载完整逻辑映射快照是不同操作。

```csharp
engine.State.CardBlacklist ??= new CardBlacklistPolicy(
    new Dictionary<string, long>(), simulatedServerUtcTicks);
engine.State.CardBlacklist = engine.State.CardBlacklist
    .WithServerUtcTicks(simulatedServerUtcTicks)
    .WithSessionEntries(sessionEntries, sessionValid, connected);
```

`sessionEntries` 是按服务器数组顺序排列的 `IEnumerable<KeyValuePair<string,long>>`（card_type、截止 ticks），已有规范名也可使用。策略转换为符号 FName 身份：仅折叠 ASCII 大小写，处理 NUL、合规数字后缀、None 和长度边界；不同非 ASCII 字符保持区别。等价键末项覆盖。无效或未连接时不合并条目；返回不可变策略，不修改旧策略。调用方仍须提供正确会话门和模拟服务器时间；自动初始化、等待/重试和刷新/清空时机尚未还原。
